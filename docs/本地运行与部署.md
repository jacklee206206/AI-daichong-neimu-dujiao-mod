# 本地运行与部署

这份文档安装的是本仓库的改造版。新数据库没有生产商品、支付渠道、代理账号、API 密钥或任何卡密，需要在自己的后台配置。

## 1. 两种运行方法

| 方法 | 需要准备 | 适合 |
| --- | --- | --- |
| Docker Compose | Docker、Compose、Python 3 | 本地启动，或已有 Linux 服务器部署 |
| 源码编译 | Go 1.26.5、Node.js 24 或更新版本、pnpm 10.34.3、Redis 7、Python 3 | 修改程序、查看代码及独立二进制部署 |

版本取自包内 `go.mod`、前端 `package.json` 和 Dockerfile。Docker 会从本仓库构建两个前端与 Go 后端。

## 2. Docker Compose 启动

在仓库根目录执行：

```sh
python3 scripts/init_config.py --docker
docker compose up -d --build
docker compose logs --tail=100 app
```

初始化时输入自己的管理员用户名、强密码并确认。脚本生成三个独立密钥，写入权限为 `0600` 的 `app/config.yml`；已有文件会拒绝覆盖。运行配置已被 Git 忽略。

默认端口只绑定本机：

- 商城：`http://127.0.0.1:8080/`
- 后台：`http://127.0.0.1:8080/admin`

Redis 不开放到宿主机公网。持久化数据放在 `state/db`、`state/uploads`、`state/logs` 和 `state/redis`，已被 Git 忽略。

启动配置关闭邮件、托管分销和真实支付。需要邮件注册或通知时，再配置自己的 SMTP。需要托管分销时，继续完成下面的域名设置。这个配置不会替你申请商户或供应商账号。

## 3. 源码编译

安装工具后，在仓库根目录执行：

```sh
corepack enable
python3 scripts/init_config.py
sh scripts/build_fullstack.sh
cd app
../bin/dujiao-next -mode all
```

本机 Redis 需要监听 `127.0.0.1:6379`。`all` 同时运行 API 与后台任务，支持付款后采购、状态恢复和同步。构建脚本内嵌两个前端并保持 `BuildType=source`。

需要前端热更新时，分别在三个终端启动：

```sh
# 终端 1，在 app 目录
go run ./cmd/server -mode all
```

```sh
# 终端 2，在 app/frontend/user 目录
pnpm install --frozen-lockfile
pnpm run dev
```

```sh
# 终端 3，在 app/frontend/admin 目录
pnpm install --frozen-lockfile
pnpm run dev
```

用户端为 `http://127.0.0.1:5173/`，管理端为 `http://127.0.0.1:5174/`。后台 API 为 `8080`。开发时保持请求 Host，代理店铺识别才有正确上下文。

## 4. 配置自己的主站

生产 Linux 主机可以把仓库放到 `/srv/evan-ai-shop`，按照 Compose 方法启动。安装 Nginx、Certbot 及其 Nginx 插件，将 `ops/nginx-main.conf.example` 中的示例域名换成自己的主站域名，并放进 Nginx 的 `http` 配置上下文。

示例保留 Host，转发到 `127.0.0.1:8080`，并注册 `dujiao_safe` 日志格式，域名运维脚本也使用此格式。请求查询字符串不会写入这份访问日志。

先将主站根域名和 www 的 DNS 指向自己的服务器，确认 HTTP 可用，再申请自己的证书。例如：

```sh
sudo nginx -t
sudo systemctl reload nginx
# 替换成自己拥有的真实域名；example.com 是文档占位。
sudo certbot --nginx -d shop.example.com -d www.shop.example.com
```

修改 `app/config.yml` 的 `reseller.main_hosts`，写入自己实际使用的主站域名。Compose 网络下，Nginx 转发可能表现为容器网关来源；`server.trusted_proxies` 应填写实际代理地址或网段。只有确认反向代理设置后，才启用 `trusted_forwarded_host`。主站和代理入口都需要能保持原始 Host。

## 5. 打通商品、支付和上游

先在管理后台完成这些配置：

1. 站点设置：名称、图标、Banner、联系方式、弹窗公告。
2. 支付渠道：填自己的商户配置；启用需要的方式，停用不使用的方式；填写真实费率。商城自收费用使用 `fee_rate`；聚合平台自己加收的费用使用 `gateway_customer_fee_rate` 展示，避免重复填写。
3. 上游连接：填自己的上游网址、API Key、API Secret，检测连接并查询商品。
4. 商品映射：将本地商品、规格与上游商品、规格关联；设置交付方式、零售价和成本价。
5. 代理供价与最低售价：控制托管店铺的定价规则；商品 API 供价单独设置。
6. 订单页面：补充实际兑换入口、订阅时长及使用说明。

每增加一个新商品，都要核对规格映射、上游库存、上游余额、采购权限和交付说明。商品上架开关本身不会建立采购映射。

聚合支付平台若自己在收银台加收费用，配置外部费用的展示与快照即可，不能又在商城的发起金额上重复加收。USDT 需要指定实际支付服务支持的网络和币种，以收银台精确到账数字为准。

## 6. 开启托管代理独立域名

主站后台允许代理后，代理在自己的账号中申请店铺、提交域名、设置 DNS、等待接入状态就绪，再装修和定价。

### 方案 A：直接到自己的服务器

平台配置示意：

```yaml
reseller:
  enabled: true
  main_hosts:
    - shop.example.com
    - www.shop.example.com
  trusted_forwarded_host: false
  domain_verification_required: true
  domain_auto_connect_enabled: true
  domain_connect_mode: legacy
  domain_entry_ip: "填写自己的服务器公网IPv4"
  settlement_confirmation_mode: auto
```

把这些字段合并到原有 `reseller` 配置中，不要增加第二个同名顶层节。代理按页面要求配置 A 和专属 TXT 记录。证书运维任务签发源站证书，后端再检查归属、HTTPS 和探针。

### 方案 B：统一 CNAME 入口

平台先在自己的 Cloudflare zone 启用并配置 Cloudflare for SaaS、回退源站与平台入口，然后配置：

```yaml
reseller:
  enabled: true
  main_hosts:
    - shop.example.com
    - www.shop.example.com
  domain_verification_required: true
  domain_auto_connect_enabled: true
  domain_connect_mode: cloudflare_saas
  domain_entry_host: entry.shop.example.com
  domain_entry_ip: "填写自己的源站公网IPv4"
  cloudflare_saas:
    zone_id: "填写自己的平台zone ID"
    api_token_file: /run/secrets/cloudflare-saas-token
    fallback_origin: origin.shop.example.com
```

平台令牌放在受限文件里，由应用账号读取。Compose 部署时，将自己的令牌保存到仓库下被忽略的 `secrets/cloudflare-saas-token`，权限为 `0600`；使用 `compose.saas.example.yml` 追加只读挂载：

```sh
docker compose -f compose.yml -f compose.saas.example.yml up -d --build
```

挂载后的容器路径为 `/run/secrets/cloudflare-saas-token`。修改运行配置后重启应用；宿主机单独创建文件不会自动出现在容器里。Cloudflare 中的回退源站必须先可用。代理添加页面生成的根域名、www、TXT 和可能需要的证书验证记录。是否开启橙色代理以页面当前提示和所用接入模式为准。

支持的 DNS 自动配置适配器是 Cloudflare、阿里云 DNS 和腾讯 DNSPod。代理通过自己的最小权限凭据授权；购买域名的平台可以不同。其他 DNS 平台走手动设置。

### 安装源站证书任务

`ops/` 中的工具适用于 Linux + systemd + Nginx + Certbot + SQLite。PostgreSQL 部署不能直接使用这个 SQLite 队列工具。系统依赖包括 `dig`、`curl`、`nginx`、`certbot`、`systemctl`。

将两个 Python 脚本安装到 root 管理的目录：

```sh
sudo install -d -m 755 /usr/local/lib/dujiao-next
sudo install -m 755 ops/provision-reseller-domain.py /usr/local/lib/dujiao-next/
sudo install -m 755 ops/auto-provision-reseller-domains.py /usr/local/lib/dujiao-next/
sudo install -m 600 ops/dujiao-reseller-domains.env.example /etc/dujiao-reseller-domains.env
sudo install -m 644 ops/dujiao-reseller-domains.service /etc/systemd/system/
sudo install -m 644 ops/dujiao-reseller-domains.timer /etc/systemd/system/
```

编辑 `/etc/dujiao-reseller-domains.env`：填公网 IPv4、证书通知邮箱、SQLite 文件绝对路径。Compose 部署默认数据库位于 `/srv/evan-ai-shop/state/db/dujiao.db`，请按真实安装目录修改。

脚本依赖 `/etc/nginx/sites-available` 和 `sites-enabled`，Nginx 必须已加载 `dujiao_safe` 日志格式。只处理已允许的代理、已验证的域名和明确提出的自动接入申请。默认只读，开启 `--apply` 后才申请证书和更新队列。

先在服务器执行一次只读检查，替换实际参数：

```sh
sudo python3 /usr/local/lib/dujiao-next/auto-provision-reseller-domains.py \
  --db /srv/evan-ai-shop/state/db/dujiao.db \
  --entry-ip YOUR_PUBLIC_IPV4 --email YOUR_EMAIL
```

确认环境后启用定时任务：

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now dujiao-reseller-domains.timer
sudo systemctl list-timers dujiao-reseller-domains.timer
```

任务只把源站证书标记为已签发；域名最终启用仍由 Go 服务独立检查。脚本不覆盖其他工具的 Nginx 配置。

## 7. 开启商品 API 与钱包

商品 API 面向有自己网站的商家。商家在个人中心申请 API 并生成凭据，在自己服务器按对应协议配置连接，再充值采购钱包和导入商品。

管理员通过 API 对接管理查看账号、设置申请自动审批策略；通过商品的 API 供货价入口修改价格；通过钱包与充值记录查看用户的采购余额与流水；订单列表查看商家向本站采购的订单。

钱包充值渠道可以只保留 USDT；具体启用哪些渠道属于后台数据库设置，不会随源码自动带入。代理利润钱包与 API 采购钱包分别处理。

## 8. 运行、更新与备份

持久化备份应覆盖 SQLite 数据库、上传目录、受限配置及必要令牌。运行中的 SQLite 应使用数据库备份方式，或停应用后完整备份；单独复制一个正在写入的 `.db` 可能遗漏 WAL 内容。

升级本分支时，先备份，再用自己的源码重建。Docker 执行 `docker compose up -d --build`；二进制部署重新执行构建脚本并替换程序。保留对应源码版本，避免用官方安装器覆盖定制版。

可运行的检查命令：

```sh
python3 scripts/check_public_package.py
python3 ops/test-provision-reseller-domain.py
python3 ops/test-auto-provision-reseller-domains.py
```

安装 Go / pnpm 后，还可以在 `app` 目录运行 `go test ./...`，在两个前端目录运行 `pnpm test` 与各自构建命令。本包当前完成哪些检查见[发布包检查记录](发布包检查记录.md)。
